# M5.5 plan — scenario-owned orders of battle

Status: implemented (M5.5 complete).
Scope: rework the M5 scenario model and builder so scenarios own their orders of
battle, units are built directly in the scenario builder, the echelon model is
simplified, and armies can be generated semi-procedurally.

## Confirmed decisions

- A scenario contains **one order of battle** containing all factions/units.
- Creating a scenario chooses **only a terrain map**; the OOB starts empty.
- The scenario OOB is built and edited in the scenario builder, not loaded from
  a roster.
- The Army Roster workspace remains as an optional reusable template library;
  scenarios never load it automatically.
- Supported echelons are **army, corps, division, brigade** only. Brigade is
  always the smallest unit.
- Legacy rosters/scenarios using `regiment` or `other` echelons are
  auto-migrated safely.
- The generator uses per-arm brigade counts and average strengths, and creates
  homogeneous formations.
- Scenarios remain in-memory in M5.5; persistence stays in M7.
- The map is chosen at creation only; no “change map” action yet.

## 1. Target domain model

Rename the scenario’s embedded roster to make ownership explicit:

```ts
BattleScenario {
  terrainSnapshot: TerrainMap
  orderOfBattle: ArmyRoster   // scenario-owned, smallestUnitEchelon: 'brigade'
  phases: BattlePhase[]
  activePhaseId: string
  ...
}
```

- Keep reusing the `ArmyRoster` shape under `orderOfBattle` so existing naming,
  hierarchy, strength, and validation helpers keep working.
- Keep `smallestUnitEchelon` in the shape but force it to `'brigade'`; remove
  the setting from the UI.
- `createScenarioDocument` changes to accept only the map plus an optional
  initial OOB:

```ts
createScenarioDocument({
  name,
  description?,
  terrain,
  orderOfBattle?, // usually omitted; creates an empty brigade-based OOB
})
```

- New scenarios get an empty OOB named “{Scenario name} order of battle”.
- The seed/demo scenario keeps a populated OOB so the app still opens with a
  useful demo.
- Scenario schema preprocesses `rosterSnapshot` into `orderOfBattle` for legacy
  documents.
- Scenario validation still rejects phase states or annotations referencing
  unknown units.
- Terrain remains a deep snapshot; editing the library map later cannot mutate
  the scenario.

## 2. Scenario creation flow

`NewScenarioDialog` becomes map-only:

- Name and description.
- One “Terrain map” picker listing saved maps with dimensions and feature
  count.
- Default selection is the currently active terrain map, otherwise the first
  saved map.
- Summary explains: “The scenario receives a snapshot of this map and starts
  with an empty order of battle.”
- Remove roster loading, roster save flushing, and the roster validation error
  path.
- If no maps exist, show a clear prompt to create one in the Terrain workspace.

The toolbar and inspector stop saying “roster snapshot” and show “Order of
battle” with faction/unit counts. The scenario cannot change maps after
creation.

## 3. Scenario builder and OOB menu

Rename the toolbar’s **Units** mode to **Order of battle**. Terrain mode stays
read-only map inspection. The left panel becomes the editable OOB menu.

Proposed layout:

```text
┌ Order of battle ────────────────────────────────┐
│ 12 formations · 2 factions                      │
│ [+ Faction]  [+ Unit]  [Generate army]         │
│                                                 │
│ ● Northern League            12/12 deployed    │
│   Army of the North        A  12,000   Remove   │
│     I Corps                C   9,000   Remove + │
│       Voss Division        D   6,000   Remove + │
│         1st Brigade        B   1,800   Remove   │
│         2nd Brigade        B   1,700   Remove   │
│ ● Southern Crown              0/8 deployed     │
│   ...                                           │
└─────────────────────────────────────────────────┘
```

### Actions in the OOB panel

- **+ Faction**: add/edit faction name, color, label color, naming modes,
  default strengths, notes.
- **+ Unit**: add a formation directly to the OOB.
- **Generate army**: opens the semi-procedural generator.
- Per-row **+**: add a subordinate under a valid parent.
- Per-row **Deploy / Remove from map**: keep the existing deployment workflow.
- Unit rows remain selectable, Shift-clickable, and hierarchy double-clickable.

### Add/edit unit form

Fields:

- Faction
- Parent formation (optional; safe reparent validation)
- Echelon: army / corps / division / brigade
- Unit type: infantry / cavalry / artillery / other
- Custom name (optional; generated-name preview)
- Commander (optional)
- Initial strength: **only shown for brigades**; higher formations show
  “Strength rolls up from brigades”
- Notes

After adding, the unit is selected. The form also gets a convenience action
such as **Add and place** so a unit can be added and then placed on the map
without a separate trip to Deploy. Adding alone does not auto-deploy.

### Editing selected units

Extend `ScenarioInspector` with an “Order of battle” section for the selected
unit:

- identity fields: name, commander, type, echelon, parent, notes
- brigade strength
- delete unit
- existing deployment fields remain when the unit is deployed

Deleting a unit:

- is blocked while it has subordinates;
- shows a confirmation if it is deployed;
- removes its phase states from **all phases** and clears annotation links in
  one undoable edit.

All OOB edits use the scenario’s existing history, so adding, reparenting,
deleting, and generating each produce one undo entry.

## 4. Semi-procedural army generator

Add a **Generate army** dialog reachable from the OOB panel. It builds one
faction’s army and appends it to the scenario OOB.

### Inputs

- Faction: existing faction, or create a new faction with name/color.
- Structure:
  - Independent brigades
  - Divisions (`N` brigades per division)
  - Corps (`N` divisions per corps, plus brigades per division)
  - Army (one army containing arm-specific corps)
- Arm rows side by side:

```text
Arm          Brigades   Strength mode     Value    Total
Infantry     [10]       [Rough average]   [3000]   30,000
Cavalry      [4]        [Rough average]   [900]     3,600
Artillery    [2]        [Exact total]     [800]       800
                                               Army total: 34,400
```

- Each arm row has a brigade count and either:
  - **Rough average strength per brigade** (default), or
  - **Exact total personnel**, from which the average is derived.
- Show the row total live, plus the combined army total and formation counts.
- Zero-brigade arms are skipped.
- Average strength must be positive when brigades are present.

### Homogeneous grouping

All formations below army level are homogeneous by arm:

- `10 infantry brigades, 3 per division` → 4 infantry divisions: 3+3+3+1
  brigades.
- `4 cavalry brigades, 3 per division` → 2 cavalry divisions: 3+1.
- `Corps` structure groups divisions of the same arm into corps.
- `Army` structure creates one mixed army containing the arm-specific corps.
- Remainders produce smaller formations rather than empty ones.
- Higher formations get `initialStrength: null`; strength rolls up from
  brigades.
- Brigade `unitType` is the arm; homogeneous division/corps types match the
  arm; the army root uses `other`.
- Generated units leave custom names blank so the faction’s naming rules
  apply. Optional army name can be set.
- Generated units are **not auto-deployed**; the user deploys them afterward.

Generate is atomic: the whole army is appended in one history entry. The dialog
shows a preview tree and rejects invalid counts/strengths before committing.

## 5. Echelon simplification and migration

### Supported model

- `UnitEchelon = 'army' | 'corps' | 'division' | 'brigade'`.
- `smallestUnitEchelon` is always `'brigade'`.
- Remove `regiment` and `other` from:
  - unit create/edit echelon pickers
  - display font/frontage/name grids
  - faction naming-mode and default-strength tables
  - roster settings and tests
- `unitType: 'other'` stays available; the restriction is about **echelons**,
  not unit types.

### Legacy auto-migration

Run migration before schema validation for rosters and scenarios:

1. Map `regiment` → `brigade` and `other` → `brigade`.
2. If a migrated unit would sit under an equal-or-lower-rank parent, lift it to
   the nearest valid army/corps/division ancestor. If none exists, make it a
   root formation.
3. Force `smallestUnitEchelon` to `brigade`.
4. Add missing supported keys to faction naming modes and default strengths;
   drop unsupported echelon keys.
5. Preserve unit IDs, names, commanders, strengths, and as much hierarchy as
   possible.
6. Persist migrated roster library documents after load/import and show a small
   notice such as “3 legacy echelons migrated to brigade.”
7. Scenario legacy field `rosterSnapshot` is renamed to `orderOfBattle` during
   the same preprocessing.

This deliberately may flatten unusual legacy `regiment`/`other` chains, so the
migration must be covered by tests.

## 6. Store and code architecture

### Shared roster operations

Extract the mutation logic currently inside `rosterStore` into reusable pure
functions, for example `features/army/rosterMutations.ts`:

- `addFaction`, `updateFaction`, `deleteFaction`
- `addUnit`, `updateUnit`, `reparentUnit`, `deleteUnit`
- shared validation and error messages

Both `rosterStore` and `scenarioStore` call these helpers. This avoids
duplicating hierarchy/cycle rules.

### Scenario store additions

- Replace all `document.rosterSnapshot` references with
  `document.orderOfBattle`.
- Add scenario actions:
  - `addFaction`
  - `updateFaction`
  - `deleteFaction`
  - `addUnit`
  - `updateUnit`
  - `reparentUnit`
  - `deleteUnit`
  - `generateArmy`
- Each action validates the whole scenario and commits one history entry.
- Unit deletion cascades across phases and annotation links.
- Removing a unit from the OOB clears it from the current selection.
- Deployment continues to read from the scenario OOB and phase state remains
  phase-local. Editing OOB strength does not rewrite already-deployed effective
  strength.

## 8. Implementation order

1. **Model and migration** — four echelons, fixed brigade, scenario
   `orderOfBattle`, legacy migration, schema tests.
2. **Generator core** — pure army generator + tests.
3. **Scenario data flow** — map-only creation, scenario store OOB actions,
   deletion cascade, history tests.
4. **Scenario builder UI** — OOB menu, add/edit unit and faction dialogs,
   inspector editing, empty states.
5. **Generator UI** — dialog, preview, append action, e2e coverage.
6. **Army workspace cleanup** — remove unsupported echelon/smallest-unit
   controls, migrate library docs, update docs and full regression.

Each phase should leave the app buildable and testable, per the repository’s
milestone contract.

## 9. Acceptance criteria

- A scenario is created by choosing a saved map; no roster is loaded.
- Each scenario owns one OOB containing all factions and units.
- The scenario builder can freely add, edit, delete, reparent, and deploy units.
- The OOB menu has faction, unit, and generator actions directly in the left
  panel.
- Only army/corps/division/brigade are available; brigade is always the
  smallest unit.
- Legacy documents auto-migrate without invalid hierarchies.
- The generator accepts per-arm brigade counts and average/exact strengths,
  produces homogeneous formations, and commits as one undoable edit.
- Source terrain edits cannot mutate existing scenarios.
- All typecheck, lint, formatting, unit, build, and Playwright checks pass.

## Out of scope for M5.5

- Scenario persistence and reload recovery (M7).
- Replacing the map after scenario creation.
- Auto-deploying generated armies.
- Automatically importing saved rosters into scenarios.
- M6 phase management and annotations.
- Removing `unitType: 'other'` unless that is also desired.

## Assumptions to confirm before implementation

1. `unitType: 'other'` remains valid for command/unspecified formations; only
   the **echelon** values `regiment` and `other` are removed.
2. Generated formations use the faction’s existing naming rules; no random
   names.
